Manual y Guía de ZCode

Documentación práctica de los 5 recursos de extensión de ZCode: MCP, Skills, Slash Commands, Hooks y Plugins. Incluye pitfalls reales, flujos de diagnóstico y un asistente interactivo.

5 recursos documentados HTML5 · Sin dependencias Español
💡
Cómo usar este manual: Navega por las secciones del sidebar o usa el buscador. Marca cada sección como leída para seguir tu progreso. El Asistente de Diagnóstico te guía cuando algo no funciona.

FAQ rápida

¿Dónde viven los archivos de configuración de ZCode?

Dos ubicaciones principales según el scope:

  • User scope → ~/.zcode/cli/config.json — aplica a todos tus workspaces.
  • Workspace scope → <repo>/.zcode/config.json (o zcode.json) — versionado en el repo.

Skills y Commands tienen directorios propios dentro de cada scope.

¿Cuándo uso user scope vs workspace scope?

User scope para configuración personal global (herramientas que usas en todos los proyectos). Workspace scope para configuración específica del proyecto, versionada y compartida con el equipo.

El workspace scope siempre gana sobre el user scope cuando hay conflicto.

¿Los ${...} se expanden en todos lados?

No. Las variables ${VAR} solo se expanden dentro de los archivos de configuración de plugins. En los archivos config.json de user o workspace scope no se expanden; debes usar rutas absolutas.

¿Cuál es el orden de precedencia cuando hay conflictos?

Para MCP, Hooks y Plugins: workspace > user > plugin-defaults.

Para Skills y Commands (discovery order, el primero gana): user .zcode > user .agents > workspace .zcode > workspace .agents > plugins.

02

Conceptos y Scopes

ZCode organiza toda su configuración en scopes (ámbitos). Entender cuáles existen y cómo se resuelven los conflictos evita el 90 % de los problemas de configuración.

Los dos scopes principales

Scope Directorio raíz Cuándo usar ¿Se versiona?
User ~/.zcode/ Configuración personal, aplica a todos los proyectos No (local)
Workspace <repo>/.zcode/ Configuración del proyecto, compartida en equipo Sí (en Git)

Archivos de configuración

User Scope — ~/.zcode/
cli/config.json MCP, Hooks, Plugins
skills/ skills personales
commands/ commands personales
~/.agents/skills/ fallback cross-client (Claude, Cursor...)

Workspace Scope — <repo>/
.zcode/config.json o zcode.json
.zcode/skills/
.zcode/commands/
.agents/skills/ fallback cross-client
.agents/mcp.json solo si no hay MCP en .zcode

Orden de descubrimiento de Skills y Commands

El sistema recorre los directorios en este orden. El primer archivo que casa gana (shadowing):

  1. ~/.zcode/skills/ — user, formato nativo ZCode
  2. ~/.agents/skills/ — user, cross-client
  3. <repo>/.zcode/skills/ — workspace, formato nativo
  4. <repo>/.agents/skills/ — workspace, cross-client
  5. Plugins instalados (menor precedencia)
⚠️
Shadowing silencioso: Si defines una skill en user scope con el mismo nombre que una de un plugin, la tuya gana sin ningún aviso. Para ver qué skill está activa ve a Settings → Skills.

Resolución de conflictos por recurso

RecursoEstrategiaGana
MCP Servers Merge por nombre de servidor; workspace sobreescribe user Workspace
Skills Shadowing: primer archivo en discovery order User .zcode
Commands Shadowing: igual que skills User .zcode
Hooks Merge de arrays; se ejecutan todos los que casan Todos activos
Plugins Namespace único; sin shadowing entre plugins Instalado
03

Servidores MCP

Model Context Protocol (MCP) conecta ZCode con herramientas externas: bases de datos, APIs, sistemas de archivos y cualquier proceso que implemente el protocolo.

Ubicaciones de configuración

~/.zcode/cli/config.json → mcp.servers user scope
<repo>/.zcode/config.json → mcp.servers workspace
<repo>/.agents/mcp.json solo si el workspace scope no define MCP
~/.zcode/cli/plugins/cache/*/plugin.json → mcpServers plugins

Esquema de un servidor MCP

{
  "mcp": {
    "servers": {
      "mi-servidor": {
        "command": "npx",
        "args": ["-y", "@mi-org/mcp-server"],
        "env": {
          "API_KEY": "valor"
        },
        "timeoutMs": 30000,
        "disabled": false
      }
    }
  }
}
🚨
Campos críticos: command debe ser un string, no un array. Usa env (no environment) y headers (no http_headers). Una clave desconocida hace que el servidor sea descartado silenciosamente.

Pitfalls frecuentes

  1. 01 El servidor aparece como failed en Settings → MCP
    el proceso no arranca o el handshake inicial falla.
    comprueba que el comando exista en el PATH. Prueba ejecutar el command + args en la terminal para ver el error real.
  2. 02 El servidor no aparece aunque está en el config
    una clave desconocida en el objeto del servidor descarta toda la entrada.
    valida el JSON. Campos válidos: command, args, env, url, headers, timeoutMs, disabled.
  3. 03 command definido como array (estilo OpenCode)
    confusión con otros clientes AI que aceptan command: ["npx", "..."].
    separa en "command": "npx" y "args": ["-y", "..."].
  4. 04 Las variables ${VAR} no se expanden en el config
    la expansión solo ocurre en configs de plugin, no en user/workspace.
    usa rutas absolutas o variables de entorno del SO.
  5. 05 Timeout al arrancar el servidor
    el servidor tarda más de 30s en responder el handshake.
    añade "timeoutMs": 60000 (o más) al objeto del servidor.
  6. 06 HTTP server: las cabeceras no se envían
    uso de http_headers en lugar de headers.
    renombra a "headers": { "Authorization": "Bearer ..." }.
  7. 07 Variable de entorno no llega al proceso MCP
    uso de environment en lugar de env.
    cambia la clave a "env": { ... }.
  8. 08 Servidor funciona en user pero no en workspace
    el workspace config define el mismo servidor con disabled: true o URL diferente.
    abre <repo>/.zcode/config.json y verifica el bloque mcp.servers.
  9. 09 JSON inválido en config.json
    coma extra o comilla sin cerrar.
    valida con cat config.json | python -m json.tool o usa un editor con linting JSON.
  10. 10 El servidor conecta pero las herramientas no aparecen en el prompt
    el servidor no exporta herramientas o el handshake de capability está incompleto.
    consulta los logs del servidor. Verifica que responde al método tools/list de MCP.
  11. 11 Instalación de plugin falla con RPC failed
    proxy corporativo o red restringida sin configurar en ZCode.
    ZCODE_HTTP_PROXY=http://host:puerto zcode …. La variable http_proxy estándar no se lee.

Workflow de localización de problemas MCP

  1. Abre Settings → MCP y lee el estado del servidor: connected, failed, disabled o ausente.
  2. Si es failed: ejecuta el command + args en la terminal directamente para ver el error.
  3. Si está ausente: valida el JSON del config con un linter y revisa campos desconocidos.
  4. Si las herramientas no aparecen: revisa la salida del protocolo MCP (tools/list).
  5. Si hay conflicto user vs workspace: abre ambos configs y compara los bloques mcp.servers.
04

Skills

Las skills son instrucciones contextuales que el modelo carga automáticamente cuando la descripción de la skill es relevante para la tarea en curso. No son comandos explícitos: el modelo decide.

💡
Cargar ≠ Disparar: Una skill puede estar cargada (visible en Settings → Skills) pero no disparar si la descripción no es suficientemente descriptiva. El trigger es semántico, no por keyword.

Estructura de un SKILL.md

---
name: mi-skill
description: |
  Breve descripción de cuándo usar esta skill (≤ 1024 caracteres).
  Los primeros ~250 caracteres son los más relevantes para el trigger.
---

# Instrucciones de la Skill

Contenido completo de las instrucciones para el modelo...

Directorios de descubrimiento (en orden)

1. ~/.zcode/skills/<nombre>/SKILL.md
2. ~/.agents/skills/<nombre>/SKILL.md
3. <repo>/.zcode/skills/<nombre>/SKILL.md
4. <repo>/.agents/skills/<nombre>/SKILL.md
5. plugins instalados (menor precedencia)

Pitfalls frecuentes

  1. 01 La skill no aparece en Settings → Skills
    el frontmatter YAML falta o está mal formado (falta name).
    añade un bloque --- al inicio del SKILL.md con name: y description: obligatorios.
  2. 02 La skill aparece pero nunca dispara
    descripción vacía, genérica o truncada (límite: 1024 chars).
    pon el trigger wording en los primeros ~250 caracteres de description. Sé específico.
  3. 03 Mi skill está sombreada por otra
    tu skill está en .agents/ y otra con el mismo nombre está en .zcode/ con mayor precedencia.
    mueve tu skill de ~/.agents/skills/ a ~/.zcode/skills/ para ganar la mayor precedencia.
  4. 04 El archivo no se llama exactamente SKILL.md
    el sistema busca el archivo con ese nombre exacto, en mayúsculas.
    renombra a SKILL.md exactamente. skill.md o Skill.md no se reconocen.
  5. 05 La skill dispara cuando no debería
    descripción demasiado amplia o genérica.
    acota la descripción con ejemplos de cuándo no usar la skill.

Workflow de diagnóstico de Skills

  1. Abre Settings → Skills. Si la skill no aparece → problema de descubrimiento (frontmatter o ubicación).
  2. Si aparece pero no dispara → problema de trigger. Mejora los primeros 250 chars de description.
  3. Si dispara otro skill en su lugar → shadowing. Comprueba la cadena de discovery.
  4. Prueba mencionar explícitamente el skill en el prompt para confirmar que el modelo lo conoce.
05

Slash Commands

Los slash commands son atajos de prompt almacenados como archivos .md. Se invocan escribiendo /nombre en el chat. El nombre del archivo determina el nombre del comando.

Estructura de un comando

---
description: Genera tests unitarios para el código seleccionado
---

Por favor genera tests unitarios completos para: $ARGUMENTS

Asegúrate de cubrir casos borde y usar el framework de testing del proyecto.

Reglas de nombrado

ReglaEjemplo correctoError común
Regex: ^[a-z0-9][a-z0-9_:-]{0,63}$ review-code.md Review Code.md ❌
Subdirectorio → separador : review/code.md → /review:code /review/code ❌
Sin mayúsculas, espacios ni puntos generate-tests.md Generate.Tests.md ❌

Tokens disponibles en el cuerpo

TokenDescripción
$ARGUMENTSTodo el texto escrito tras el nombre del comando
$1, $2, …Argumentos posicionales separados por espacio
⚠️
Sintaxis incorrecta: ${ARGUMENTS} con llaves no se reconoce. Usa $ARGUMENTS (sin llaves).

Pitfalls frecuentes

  1. 01 El comando no aparece en el menú /
    nombre del archivo con mayúsculas, espacios o caracteres inválidos.
    renombra siguiendo la regex ^[a-z0-9][a-z0-9_:-]{0,63}$.
  2. 02 El comando ejecuta contenido incorrecto
    otro archivo con el mismo nombre tiene mayor precedencia (shadowing).
    busca el mismo nombre en todos los directorios de commands. El primero en discovery order gana.
  3. 03 El archivo existe pero el comando se descarta
    tanto el frontmatter description como el cuerpo están vacíos.
    añade al menos una description no vacía o un cuerpo con instrucciones.
  4. 04 /review/code no encuentra el comando
    los subdirectorios usan dos puntos como separador, no slash.
    invoca como /review:code.
  5. 05 ${ARGUMENTS} no se expande en el prompt
    sintaxis incorrecta con llaves ${}.
    usa $ARGUMENTS sin llaves.
06

Hooks

Los hooks son acciones automáticas disparadas por eventos del ciclo de vida de ZCode. Permiten inyectar comportamiento sin modificar skills ni comandos.

🚨
Deshabilitados por defecto: Debes añadir "hooks": { "enabled": true, ... } en el config.json. Sin esto, ningún hook del config se ejecuta.

Los 7 eventos de hook

EventoCuándo se disparaPuede bloquear
SessionStartAl iniciar una nueva sesión de ZCodeNo
UserPromptSubmitCuando el usuario envía un mensajeSí
PreToolUseAntes de que ZCode ejecute una herramientaSí
PermissionRequestCuando ZCode solicita permiso al usuarioSí
PostToolUseTras la ejecución exitosa de una herramientaNo
PostToolUseFailureTras el fallo de una herramientaNo
StopAl terminar la sesión o el agenteNo

Tipos de ejecutor

TipoClaveUnidad de timeoutUso
command "command": "bash -c '...'" timeout en segundos Scripts shell, Python, linters
process "process": { ... } timeoutMs en milisegundos Procesos con comunicación bidireccional
⚠️
Trampa de unidades: timeout: 500 en un hook command = 500 segundos. timeoutMs: 500 en un hook process = 500 milisegundos.

Ejemplo de hook completo

{
  "hooks": {
    "enabled": true,
    "hooks": [
      {
        "event": "PostToolUse",
        "matcher": "Bash",
        "command": "echo 'Bash ejecutado' >> ~/.zcode/audit.log",
        "timeout": 5
      }
    ]
  }
}

Pitfalls frecuentes

  1. 01 El hook nunca se dispara
    falta "enabled": true en el bloque hooks del config.
    añade "hooks": { "enabled": true, "hooks": [...] } en config.json.
  2. 02 El matcher no casa con la herramienta
    el matcher es case-sensitive. "bash" no casa con Bash.
    usa el nombre exacto como aparece en los logs (ej. Bash, Edit, Write). Omite el matcher para casar todo.
  3. 03 La sesión se bloquea por un hook
    timeout: 500 significa 500 segundos de espera.
    usa un valor razonable: timeout: 5 para 5 segundos o timeoutMs: 5000 en tipo process.
  4. 04 Nombre de evento con mayúsculas incorrectas
    el sistema de eventos es case-sensitive.
    usa exactamente uno de los 7 nombres: SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Stop.
  5. 05 Los hooks de plugin no necesitan enabled: true
    solo los hooks del config.json necesitan el flag. Los de plugins se activan con el plugin.
    si el hook viene de un plugin, verifica que el plugin esté habilitado en Settings → Plugin Management.

Workflow de diagnóstico de Hooks

  1. Confirma que hooks.enabled: true está en el config del scope correcto.
  2. Verifica que el nombre del evento sea exactamente uno de los 7 (case-sensitive).
  3. Si el matcher está definido, comprueba que el nombre de la herramienta sea exacto.
  4. Si la sesión se bloquea, busca un hook con timeout demasiado alto y corrígelo.
  5. Prueba el comando del hook ejecutándolo manualmente en la terminal.
07

Plugins & Marketplaces

Los plugins empaquetan múltiples recursos (skills, commands, hooks, MCP servers) en una unidad reutilizable e instalable. Se gestionan desde Settings → Plugin Management.

Ciclo de vida de un plugin

  1. Añadir marketplace → Settings → Plugin Management → Marketplaces → Add.
  2. Instalar plugin → navega el marketplace, pulsa Install. ZCode clona el repo.
  3. Habilitar → pestaña Installed → toggle ON. Los componentes quedan activos.
  4. Configurar → si el plugin tiene userConfig, rellena los campos en la UI.
  5. Desinstalar / deshabilitar → toggle OFF o botón Uninstall.

Estructura de un manifest de plugin

{
  "name": "mi-plugin",
  "version": "1.0.0",
  "description": "Descripción breve",
  "skills": [
    { "path": "skills/mi-skill/SKILL.md" }
  ],
  "commands": [
    { "path": "commands/mi-comando.md" }
  ],
  "mcpServers": {
    "servidor-del-plugin": {
      "command": "npx",
      "args": ["@mi-org/servidor"],
      "env": { "TOKEN": "${PLUGIN_TOKEN}" }
    }
  },
  "userConfig": [
    {
      "key": "PLUGIN_TOKEN",
      "description": "Token de autenticación",
      "required": true
    }
  ]
}
⚠️
userConfig con sensitive: true — actualmente no se puede introducir desde la UI. Quita el campo sensitive o usa una variable de entorno del SO.

Pitfalls frecuentes

  1. 01 El plugin no aparece en la pestaña Installed
    el marketplace no fue añadido o la instalación falló silenciosamente.
    ve a Marketplaces y confirma que el repo esté añadido. Revisa los logs de ZCode.
  2. 02 El plugin está instalado pero sus skills no aparecen
    el plugin está deshabilitado (toggle OFF).
    en Settings → Plugin Management → Installed → activa el toggle del plugin.
  3. 03 Instalación falla con RPC failed o timed out
    proxy corporativo o red restringida.
    ejecuta ZCode con ZCODE_HTTP_PROXY=http://host:puerto. La variable http_proxy estándar no se aplica.
  4. 04 plugins.enabled: false en el config
    el subsistema de plugins fue desactivado globalmente.
    abre ~/.zcode/cli/config.json y asegúrate de que plugins.enabled sea true o que el campo no exista.
  5. 05 userConfig con sensitive: true no funciona en la UI
    limitación actual de la interfaz de ZCode.
    elimina el campo sensitive del userConfig y usa variables de entorno del SO para credenciales sensibles.
  6. 06 Un componente del plugin escapa del directorio raíz
    rutas path en el manifest con ../ que salen del directorio del plugin.
    todas las rutas deben ser relativas al root del plugin, sin ../.

Workflow de diagnóstico de Plugins

  1. Confirma que plugins.enabled no sea false en ~/.zcode/cli/config.json.
  2. En Installed, confirma que el toggle esté activado.
  3. Abre la vista de detalle del plugin para ver componentes y warnings.
  4. Si las skills/commands no aparecen, busca shadowing: tu user scope puede estar tapando los del plugin.
  5. Si el MCP del plugin no conecta, revisa su bloque mcpServers y las variables del userConfig.
08

AGENTS.md & Instrucciones

AGENTS.md es el archivo de instrucciones persistentes para el agente. Define el contexto del proyecto, convenciones de código y reglas que el modelo debe seguir en cada sesión.

Scopes del AGENTS.md

ScopeUbicaciónAlcance
User ~/.zcode/AGENTS.md Aplica a todas las sesiones de ZCode
Workspace raíz <repo>/AGENTS.md Aplica al workspace completo
Subdirectorio <repo>/src/AGENTS.md Solo cuando el agente trabaja en ese directorio

Orden de merge

Los archivos AGENTS.md se concatenan en este orden (del más general al más específico):

  1. User: ~/.zcode/AGENTS.md
  2. Workspace raíz: <repo>/AGENTS.md
  3. Subdirectorios en profundidad creciente (según el directorio actual de trabajo)
💡
Efecto acumulativo: Las instrucciones se suman, no se sobreescriben. Si tienes reglas conflictivas en user y workspace, el modelo ve ambas. Sé explícito en workspace para anular el user scope.

El comando /init

Al ejecutar /init en un nuevo workspace, ZCode genera un AGENTS.md con el contexto del proyecto (estructura, stack tecnológico, convenciones detectadas). Puedes editarlo después.

Plantilla de AGENTS.md

# Mi Proyecto — Instrucciones para ZCode

## Stack Tecnológico
- Backend: Node.js 20 + Express
- Frontend: React 18 + TypeScript
- DB: PostgreSQL 15

## Convenciones de Código
- Usa siempre `const` en lugar de `let` si no se reasigna.
- Nombres de funciones en camelCase, clases en PascalCase.
- Tests con Vitest.

## Reglas Importantes
- NUNCA commitees credenciales o API keys.
- Ejecuta `npm test` antes de proponer cambios.
- El idioma de los comentarios de código es inglés.

Migración desde .clinerules / .cursorrules

El contenido de .clinerules o .cursorrules puede copiarse directamente a AGENTS.md. ZCode también puede leer .cursorrules como fallback de compatibilidad, pero AGENTS.md tiene prioridad.
